## 1. 원인 재확인 (2026-10-18 실측)

방법: 홈 폴더에 이 시험만을 위한 임시 폴더를 만들고(작업 폴더·옆 폴더·다른 홈 폴더에 표시 파일), 엔진과 같은 `codex sandbox -P :workspace`로 명령을 돌렸다.
출력에는 참/거짓만 남기고, 시험 폴더는 곧바로 지웠다. 대장의 실제 개인 파일은 열지 않았다(권한 목록 `icacls`만 확인).

| 확인 | 결과 |
|---|---|
| 작업 폴더 안 쓰기·읽기 | 됨 |
| 작업 폴더 **옆 폴더** 파일 읽기 / 목록 | **됨 (누출)** |
| 작업 폴더와 무관한 **다른 홈 폴더** 파일 읽기 | **됨 (누출)** |
| `C:\Windows\win.ini` 읽기 | 됨 (시스템 파일, 예상된 동작) |
| 작업 폴더 밖 쓰기 | 막힘 |
| 홈 폴더 자체의 목록 | 막힘 (홈 폴더에만 읽기 거부가 걸려 있음) |
| TCP 연결(1.1.1.1:443), 웹 요청 | 막힘 |
| DNS 조회(Node `dns.lookup`) | **됨** (8차 때와 같음, 남은 위험) |
| `whoami` | `<PC 이름>\codexsandboxoffline` (관리자 모드 샌드박스 계정) |

권한이 붙는 방식: 홈 폴더에는 `CodexSandboxUsers:(DENY)(R)`와 하위로 상속되는 읽기 거부가 있다. 그런데 샌드박스를 한 번 돌리면 홈 아래 폴더마다
`CodexSandboxUsers:(OI)(CI)(RX)`가 **명시적으로** 붙고(새로 만든 시험 폴더 두 곳 모두, 작업 폴더와 무관한 쪽도), 명시 허용이 상속 거부보다 앞서므로 읽힌다.
이 권한은 실행이 끝나도 남는다.

읽기를 좁히는 시도 (모두 같은 날, 같은 CLI):

| 시도 | 결과 |
|---|---|
| 권한 프로필 `":minimal"="read"` + 작업 폴더 쓰기 (관리자 모드) | 거부: `elevated Windows sandbox requires effective :root read access` |
| 같은 프로필 + `windows.sandbox="unelevated"` | 거부: `Restricted read-only access requires the elevated Windows sandbox backend` |
| `":root"="read"` + 옆 폴더 `"deny"` (절대 경로·`~/` 경로·`**` 글롭) | **오류 없이 무시** — 표시 파일이 그대로 읽힘 |
| `windows.sandbox="mxc"` | 거부: `native MXC is unavailable on this executor` |

결론: 이 PC의 Windows 기본 샌드박스로는 "작업 폴더 밖 읽기 금지"를 만들 수 없다. 특히 `deny`가 조용히 무시되므로 프로필 설정을 믿고 켜면 안 된다.

## 3. 2차 설계 — 대장 보안 조건별 대응

| 대장 조건 | 설계 | 확인하는 시험 | 상태 |
|---|---|---|---|
| Windows 드라이브 자동 마운트 차단 | `/etc/wsl.conf` `[automount] enabled=false`, `mountFsTab=false`. 수동 마운트는 root만 가능 → 실행 사용자 sudo 없음·root 잠금 | `/mnt/c` 없음, `windowsRead`, `mountEscape`(`mount -t drvfs C:`) | 설계·시험 작성, **실측 대기** |
| Windows 프로세스 실행 연동 차단 | `[interop] enabled=false`, `appendWindowsPath=false`, `[gpu] enabled=false`(Windows 드라이버 공유 끔), 권장: `.wslconfig` `guiApplications=false` | binfmt `WSLInterop` 꺼짐, PATH에 `.exe` 없음, `interopExec`(cmd.exe·powershell.exe·`/mnt/c/...`·`/run/WSL` 소켓·`WSL_INTEROP` 소켓 연결) | 설계·시험 작성, **실측 대기** |

## 4. 격리 구조 — 한 작업의 흐름

| 순서 | 어디서 | 하는 일 |
|---|---|---|
| 1 | Windows (엔진) | 기존 작업 폴더 검사(`assertWorkspaceConfigurationSafe`) + `packFolder`: 일반 파일만 tar로 묶음 |
| 2 | 배포판, root | `install -d -o hqcodex -m 700 /srv/hq/jobs/<id>` |
| 3 | 배포판, hqcodex | `tar -x` (표준 입력) — Windows 경로는 배포판에 한 번도 나타나지 않음 |
| 4 | 배포판, hqcodex → bubblewrap | `codex exec --ignore-user-config -c permissions.hq=… -c default_permissions="hq" --cd /srv/hq/jobs/<id> -` (프롬프트는 표준 입력, `--sandbox` 안 씀) |
| 5 | 배포판, hqcodex → Windows | `tar -c --format=pax` (표준 출력) → `unpackReturn`이 검사 → **임시 폴더**에 풀기 |
| 6 | Windows (엔진) | (다음 단계) 바뀐 파일을 프로젝트에 반영 — 기존 대장 규칙(금지 경로)·완료 근거·검증팀 절차 그대로 |
| 7 | 배포판, root | `rm -rf --one-file-system /srv/hq/jobs/<id>` |

세 겹: ① Windows ↔ 배포판: 공유 폴더·드라이브·Windows 프로그램 없음 ② 배포판 안: root 아닌 전용 사용자 ③ Codex가 돌리는 명령: bubblewrap 안에서 작업 폴더만, 네트워크 없음.
Codex 본체(모델과 대화하는 프로세스)만 인터넷에 나간다. 코드는 `src/코덱스격리.js`(명령 만들기·경계 판정·시험 스크립트), `src/작업묶음.js`(묶기·반환 검사), `scripts/코덱스격리-준비.mjs`(배포판 준비·확인).

## 7. 남은 위험 — WSL로 충분한가, VM·별도 계정이 필요한가

WSL2 배포판은 Windows 사용자 권한의 연장선이다. 드라이브 자동 연결·Windows 프로그램 실행을 끈 것은 배포판 설정이므로, **배포판 안에서 root가 되면** 설정을 되돌리거나 drvfs를 손으로 연결해 Windows 사용자 파일 전체에 닿을 수 있다.

| 위험 | 막는 장치 | 남는 것 |
|---|---|---|
| R1 배포판 root 획득 → `wsl.conf` 변경·수동 drvfs 연결 | 실행 사용자 sudo 없음·root 잠금, 명령은 bubblewrap 안에서 더 좁게. (다음 단계) 매 작업 전 준비 확인을 자동으로 돌려 설정이 바뀌면 중단 | Linux 커널·setuid 프로그램 취약점 (WSL 커널은 Microsoft 업데이트) |
| R2 WSL VM 탈출 (하이퍼바이저·파일 서버 취약점) | — | 낮지만 0이 아님. 성공하면 대장 Windows 계정 권한 |
| R3 같은 사용자의 작업끼리 분리 | bubblewrap가 작업 폴더만 보임 + 작업 폴더 700 + 끝나면 삭제 | 옆 작업 폴더 읽기·쓰기 막힘 **실측**. 두 작업이 **동시에** 도는 경우는 미실측 |
| R4 네트워크 | 명령은 bubblewrap 네트워크 차단, 배포판 자체는 Codex 본체 때문에 인터넷 필요 | TCP·DNS 막힘 **실측**. 배포판 안에서 샌드박스 밖으로 도는 프로그램(Codex 본체)은 인터넷 가능 |
| R7 WSL 연동 소켓 | `/run/WSL/1_interop`가 누구나 접속 가능하게 열려 있음. 샌드박스 안에서는 접속 막힘, Windows 실행 요청은 Windows 쪽이 받지 않음(실측) | 소켓 자체는 WSL 구성 요소라 지우지 않음 |
| R5 돌려받은 파일 내용 (악성 코드·프롬프트 주입) | 에이전트 설정 파일은 반환 거부, 이후 기존 대장 규칙·감시·검증팀 그대로 | 경계 문제가 아니라 내용 검토 문제 |
| R6 엔진 쪽 `wsl -u root` | 엔진(Windows)은 신뢰 영역, Codex는 Windows에 닿지 못함 | — |

판단:
- **AGENT HQ 프로젝트 코드와 Codex가 쓴 코드를 다루는 일**에는, WSL 실측이 모두 통과하면 WSL 구조로 충분하다고 제안한다 (R1·R2가 커널 취약점급 공격을 요구).
- **출처를 모르는 외부 코드·패키지를 설치하거나 실행하는 일**(네트워크 켠 `npm install` 등)은 WSL 경계로 부족하다 → 그때는 **Hyper-V VM**(Education 판 지원, 기능 켜기 필요)을 쓴다.
  별도 Windows 계정은 대장이 1차에 거절했고, 이 PC에서 Codex 자체 샌드박스 계정도 폴더 권한 부여로 무력화된 것을 봤으므로 VM이 더 낫다.
- WSL 실측(2026-10-18)에서 VM 전환을 요구하는 누출은 **나오지 않았다.** 남은 것은 커널·가상화 취약점급(R1·R2)과 동시 작업 미실측(R3)이다.

### 승인 표시(`AGENT_HQ_ARCH_APPROVED=대장`)의 한계와 보완 제안

점검 결과, 지금의 승인 표시는 **대장 승인을 증명하지 못한다.**

| 약점 | 내용 |
|---|---|
| 누구나 설정 가능 | 환경변수는 같은 계정에서 도는 모든 프로그램(AI 세션 포함)이 붙일 수 있다. 값이 `대장`인지만 본다 |
| 훅 우회 | `git commit --no-verify`, `git -c core.hooksPath=/dev/null commit`, `.git/config`의 `core.hooksPath` 변경으로 검사 자체를 건너뛸 수 있다 |
| 무엇을 승인했는지 없음 | 승인이 특정 변경 내용에 묶여 있지 않다. 승인 뒤 내용을 바꿔도 같은 표시로 통과한다 |
| 기록 없음 | 누가 언제 무엇을 승인했는지 남지 않는다 |

보완 제안 (대장이 통제하는 비밀 + 변경 해시 결합, 설치·구현은 대장 승인 후):

1. **승인 기록 = 서명된 해시.** 대장만 가진 서명 키(예: 비밀번호를 건 SSH 키, 가능하면 Windows Hello·FIDO 보안 키에 묶인 `ed25519-sk`)로,
   보호 파일 변경 내용의 해시(`git diff --cached`의 보호 파일 부분, 또는 변경 후 각 보호 파일의 sha256 목록)에 서명한다:
   `ssh-keygen -Y sign -n agent-hq-arch -f <대장 키> approval.txt`. AI는 키의 비밀번호·터치 없이 서명할 수 없다.
2. **승인 기록은 리포에 남긴다.** `approvals/<날짜>-<해시 앞 12자>.txt`(무엇을 승인했는지 + 해시) 와 `.sig`. 대장의 공개 키만 `approvals/allowed_signers`에 두고,
   이 파일 자체도 보호 파일로 한다.
3. **검사는 서명을 확인한다.** `scripts/아키텍처-검사.mjs --staged`가 보호 파일 변경의 해시를 다시 계산해, 그 해시에 대한 유효한 서명 기록이 있을 때만 통과
   (`ssh-keygen -Y verify -f approvals/allowed_signers -I 대장 -n agent-hq-arch -s approval.txt.sig`). 환경변수는 더 이상 근거가 아니다.
4. **훅 우회 대비:** 같은 검사를 `npm test`(`test/아키텍처가드.test.js`)에도 넣어, 보호 파일의 현재 내용 해시가 마지막 서명 기록과 맞지 않으면 실패하게 한다.
   훅을 건너뛰어도 테스트와 서버 시작 검사에서 드러난다. 가능하면 GitHub에 올릴 때 서명 커밋·브랜치 보호도 함께.
5. 이번 커밋은 지금 규칙대로 환경변수 표시로 했다. 위 방식이 구현되면 이번 변경도 대장이 서명해 소급 기록할 수 있다.

### 11-7. WSL2로 충분한가 — 다시 평가

이번 시험에서 Windows 개인 파일·인증정보·엔진 보호 파일이 Codex에 노출된 경우는 **없다.** 엔진 폴더와 보호 파일이 든 폴더, 홈·드라이브 전체는 보내지 못하게 막았다(`checkProjectFolder`).
남은 위험은 7절의 R1(배포판 root 획득), R2(VM 탈출) 같은 커널·가상화 취약점급이다. 실행 전 점검이 설정·setuid·sudo 변화를 매번 확인하므로, R1이 남기는 흔적(설정 변경, 새 setuid, sudo)은 다음 작업 전에 드러난다.
판단은 7절과 같다: **AGENT HQ 프로젝트 코드 수준은 WSL 구조로 충분, 출처 모를 외부 코드·패키지 실행은 Hyper-V VM.** 지금 VM으로 바꿔야 할 근거는 나오지 않았다.

### 반환 파일 보안과 원자적 반영 (4번)

시험: 교체 도중 1·2·3·4·5번째 이름 바꾸기에서 일부러 실패시켜도 매번 프로젝트가 원래 해시로 돌아왔다. 남는 임시·백업 파일 없음.

### 관측·기록 연동 (5번)

하네스는 운영과 같은 모양으로 남긴다: `goals`, `runs`(팀 `team`, 도구 `executor`, 요청·실제 모델 `requestedModel`·`actualModel`, 시작·끝 시각, `outcome`, `checkpoint`의 추가·수정·삭제 파일, **토큰 사용량 `usage`(새 필드)**, `isolation`의 충돌·거부·반영·기준 지문, 라우팅 이유), 사건 `goal.run_started`, `team.handoff`(보낸·받는 팀과 도구, 인계문과 해시), `harness.step`, `harness.verified`, `codex.blocked`·`codex.conflicts`·`codex.return_rejected`·`codex.apply_aborted`, `goal.recovery_required`, 완료 근거(`by: 'engine'`, 파일 해시, 시험 기록 해시).
엔진의 `observe()`와 `projectRecord()`가 이 기록을 그대로 읽는다(단위 시험: 팀별 단계 수, 실행 도구별 체크포인트).
사무실 화면: '팀 현황' 목록에 실행 도구 옆에 **실제 모델 이름**(없으면 "요청" 표시)을 붙였다. 책상 배지·직원 움직임·인계·승인함·프로젝트 진행 표시는 그대로이고, 화면 시험(문법·사무실 움직임) 통과.
아직 안 한 것: 운영 실행 기록에 토큰 사용량 필드를 채우는 것(운영 경로 변경이라 Codex 실전 연결 때 함께).

## 20. 서명 키 등록 순서 (결정 1) — 대장이 직접

호환성: 이 PC의 Windows OpenSSH 9.5는 보안 키(FIDO2) 경로(WebAuthn)를 갖추고 있고, `ssh-keygen -Y sign/verify`는 `ed25519-sk` 키를 지원한다 — 지금 스크립트와 원리상 호환된다.
**지금 연결된 FIDO 보안 키는 없어서 실제 키로는 시험하지 못했다.** GitHub의 Windows 실행기에서도 같은 `ssh-keygen`으로 확인한다(보안 키 서명 확인에 장치는 필요 없음).

1. 키 만들기 (C:\Windows\System32\OpenSSH\ssh-keygen.exe):
   - 보안 키: `ssh-keygen -t ed25519-sk -O verify-required -C "AGENT HQ 대장 승인" -f %USERPROFILE%\.ssh\agent-hq-approval` (PIN + 터치)
   - 보안 키를 못 쓰면: `ssh-keygen -t ed25519 -C "AGENT HQ 대장 승인" -f %USERPROFILE%\.ssh\agent-hq-approval` — **비밀번호를 꼭 걸고, ssh-agent에 올리지 않는다**
2. 공개 키 등록: 리포에 `approvals\allowed_signers` 파일을 만들고 한 줄 — `daejang namespaces="agent-hq-approval" <agent-hq-approval.pub 의 앞 두 칸>`
   (이 순간부터 서명 모드가 켜져 가드·CI가 서명을 요구한다 — 3·4를 바로 이어서 한다)
3. 초기 승인 요청 만들기: `node scripts/승인-서명.mjs --request-protected "서명 키 등록 — 보호 파일 초기 승인"` (파일을 지정하지 않으면 보호 파일 전체 + 공개 키 파일)
4. 요청 파일의 목적·대상·해시를 확인하고 서명: `ssh-keygen -Y sign -n agent-hq-approval -f %USERPROFILE%\.ssh\agent-hq-approval approvals\<요청>.json`
5. 확인: `node scripts/승인-서명.mjs` → 보호 파일 ✓. Codex 환경 기준도: `--request-baseline "Codex 환경 기준 승인"` → 서명.
6. `approvals\` 를 커밋. 그다음 `approvals/allowed_signers` 를 보호 파일 목록에 넣는 정책 변경을 요청 → 서명 → 커밋(이때부터 커밋 검사가 환경변수 대신 서명을 본다).

AI는 1·2·4를 하지 않는다. 개인 키 파일과 비밀번호는 AI 실행 환경에 주지 않는다.
